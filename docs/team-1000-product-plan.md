# EriseChat 日常聊天产品优化方案

> 设计提案 · 2026-11-13 · 基于此前对 `dev` 分支 `6ca61cc` 的 78/100 评审。本文给出设计方向、开发顺序和验收目标。

## 1. 产品定位

EriseChat 面向约 **1,000 名普通用户**，服务朋友、家人和兴趣小群的日常聊天。使用人数是全站规模。容量验证单独计算同时在线设备、群成员规模和消息流量。首发假设用户通过邀请加入，常用群为 5–30 人，用 100 人活跃群做压力场景。

用户打开应用时应能马上接着聊，随手发一张图或一段语音，翻回去也能找得到。主导航围绕消息、联系人、收藏和设置。需求取舍以这些日常动作的频率、操作成本和失败后果为依据。

## 4. 界面与视觉方案

### 4.1 首页、会话与输入区

| 场景 | 设计 |
| --- | --- |
| 手机消息首页 | 顶部「消息」与发起聊天按钮，下方搜索和「全部／未读／群聊」。每行第一层是昵称、时间，第二层是最近消息、草稿或发送失败，右侧显示未读及免打扰。底栏为消息、联系人、设置，收藏从设置入口进入。好友请求的计数归联系人。 |
| 手机聊天详情 | 顶部是返回、头像昵称、可用的「更多」。更多含搜索本会话、媒体文件、免打扰和群资料。进入聊天后隐藏底栏，把空间给历史和键盘。默认输入框一行，逐行扩展，超出 5 行后输入框内滚动。附件按钮打开照片、相机和文件，语音入口保留在输入区。 |
| 桌面 | 宽屏采用约 72px 导航栏与 300–340px 会话栏，聊天正文占剩余空间。群资料和媒体面板按需打开。窄窗口优先保留可输入空间，详情面板覆盖显示。保留现有全局搜索快捷键和桌面右键菜单，悬停或键盘聚焦显示回复和更多操作。 |
| 时间线 | 相邻同发言人的消息分组，群聊在组首展示头像和昵称。时间在组尾或详情展示，日期与首条未读各有分隔。长文本气泡限制宽度，照片、文件、语音使用各自清楚可辨的样式。浏览旧消息时收到新消息，仅更新「有新消息」按钮，点击后回最新。 |
| 空态与错误 | 无选中会话时只留一条提示。有后续动作的空态给一个主按钮。消息和附件失败贴近对应内容，提供重试或取消。断网用单一连接提示。删除不能操作的「更多」占位。 |

### 4.2 视觉方向

沿用 EriseChat 的蓝色识别，采用中性表面和少量品牌强调色。减少大面积蓝白渐变、厚阴影和连续边框，让头像、图片与消息本身承担视觉层次。浅色候选为聊天底 `#F5F7FB`、接收气泡 `#FFFFFF`、发送气泡 `#DCEAFF`、正文 `#17263A`、次级文字 `#53647B`、主操作 `#245FE3`。深色候选为聊天底 `#111827`、接收气泡 `#1F2937`、发送气泡 `#263C60`、正文 `#EEF4FC`、次级文字 `#B3C0D2`、主操作 `#A5C7FF` 配深色文字。以真实页面测量所有选中、禁用和焦点状态，再定最终色板。

消息正文默认 15–16px，时间等元信息 12–13px，列表行高以 64–72px 为起点。使用系统中文字体栈，现有字号、密度设置继续可用。主题补「跟随系统」，保留手动覆盖。主要触控区域建议 44×44 CSS px，正文与可读的次级文本目标对比度 ≥4.5:1。未读、选中、失败同时使用文字、形状或图标，键盘可见焦点，读屏能区分发送状态。 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

### 4.3 流畅感来自稳定反馈

- 点击切会话立即更新选中态，优先渲染缓存的近期消息。同一时刻只让当前会话的请求更新画面，快速连点时避免串页。
- 动效集中在抽屉、图片预览和手势回弹，常用过渡建议 120–200ms。手势可取消，尊重「减少动态效果」。消息批量到达、历史补拉时直接按序合入。
- 首次进入有未读的会话定位到未读分隔线附近。返回列表恢复原筛选、滚动位置。再次打开同一会话恢复浏览位置，提供一键回最新。只有用户在活跃会话实际看到相应进度时推进已读。
- 图片按已知尺寸预留空间，列表优先加载缩略图，打开才请求大图。向上加载历史、图片解码、引用跳转、输入框随键盘调整时，都用同一条可见消息做位置锚点。
- 发送文字先出现「发送中」，服务端确认后更新状态。断网重连按同一幂等键补发，失败重试保留文字、引用和附件状态。草稿继续按会话保存。中文输入法选词时按 Enter 不误发。

## 5. 功能优先级

| 优先级 | 工作项 | 完成标准 |
| --- | --- | --- |
| P0 | 修复会话直达与消息状态 | Web 直接打开或刷新会话链接可用，通知进入原会话时可恢复登录后跳转。弱网、双端并发、重复发送、重连后的未读和编辑撤回都通过回归。 |
| P0 | 三屏 UI 与移动端通知 | 消息列表、聊天详情和输入区完成视觉收敛及手势打磨。常见 Android 真机锁屏可收到支持场景内的提醒，桌面托盘点击进入会话，活跃会话同设备不重复提醒。普通群可选全部、仅提及、静音，锁屏消息预览由用户控制，默认隐藏正文。 |
| P0 | 邀请、隐私和基础治理 | 注册主流程用邮箱验证码。加入服务、添加好友、加入群聊各自明确确认对象。好友可通过精确用户名或可撤销个人链接添加，链接不暴露邮箱。群邀请链接支持撤销和有效期。拒绝或拉黑后阻止后续私聊与邀请，双方仍在共同群内时保留群消息语义。举报仅提交用户选中的内容，由运营人员处理。 |
| P0 | 账号与数据安全 | 清理明文记密，会话可单独撤销。Web 与客户端分别设计安全会话存储，文件、搜索、收藏统一校验访问权。备份失败可见，真实恢复核对消息与附件，发布探活能识别数据库不可用。 |
| P1 | 图片与语音好用 | 多选图片后预览、排序与删除，发送时同批图片显示为相册，失败单项可重试。语音提供录音试听、取消、重录、倍速，切换会话返回可恢复播放位置。 |
| P1 | 轻量回应、搜索和共享媒体 | 表情回应可撤销、跨端一致。全局搜索按人、群、消息分类，消息可按日期和发送人筛选，文件名及链接结果可回原会话。媒体页和搜索退出时恢复滚动位置。 |
| P2 | 按试用反馈排期 | 群已读明细、合并转发、贴纸包、视频消息与简单裁剪。iPhone 主屏幕应用的通知覆盖根据设备占比决定推进顺序。音视频通话、公开频道及端到端加密各自做独立需求和成本评估。 |

联系人和群组涉及陌生人访问时，限制应落在服务端。登录后只能用授权的会话读取消息，退群、撤回和拉黑场景同时验证搜索、收藏、附件、推送及深链接。客户端的离线缓存按账号和服务器隔离，账号切换时重新校验。现阶段消息仍由服务端保存，隐私说明应准确描述其可见范围。 [现有联系人接口](../server/Chat.Server/Api/UserEndpoints.cs) · [现有会话服务](../server/Chat.Server/Modules/Conversations/ConversationService.cs) · [会话管理参考](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

Android 先用试用群体的实际机型测锁屏、省电、切网和冷启动。现有前台连接受系统超时限制，若漏提醒超过门槛，再选覆盖目标设备的系统推送通道。iPhone 先验证移动 Web 和主屏幕 Web Push 的安装、授权及点击跳转。推送通道默认只携带会话定位所需的最少信息。正文由客户端按权限同步。 [Android 前台服务限制](https://developer.android.com/develop/background-work/services/fgs/timeout) · [WebKit 主屏幕 Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

## 6. 把「丝滑」写成发布验收

以下是建议目标。上线前用固定机型、生产构建、可复现网络条件记录基线，并分别看桌面和移动端。所有门槛都应记录测试条件。

| 项目 | 建议指标与场景 |
| --- | --- |
| 操作响应 | Web 现场 INP P75 ≤200ms，按桌面与手机分别统计。缓存命中的会话切换至首屏内容可读 P95 ≤250ms，文字点击发送至本地气泡出现 P95 ≤100ms。 [INP 指标参考](https://web.dev/articles/inp) |
| 长列表与媒体 | 在 60Hz 中端 Android 上，加载含文字、图、语音的长会话，连续滚动 30 秒，至少 95% 的帧间隔 ≤20ms。新消息到达、前插历史和图片解码时，阅读锚点漂移 ≤8 CSS px。 |
| 送达与恢复 | 模拟 80ms RTT、1% 丢包及断网重连。在线发送确认 P95 ≤500ms，另一在线客户端可见 P95 ≤1 秒。服务端已确认消息在测试中无丢失、无重复，连续序号及已读状态正确。 |
| 后台提醒 | 已授权、联网且系统允许后台提醒的设备，私聊和提及在 30 秒内显示比例 ≥98%，按平台与机型报告。强停、离线、权限关闭分别记录，避免把限制场景混在成功率里。 |
| 查找与易用性 | 中文两字词、文件名及发送人筛选的搜索首屏 P95 ≤1.5 秒。至少 8/10 名首次试用者能在 3 分钟内完成加入、找到好友、发送图片，至少 8/10 能在 30 秒内从已有聊天找回指定图片。 |
| 布局与可访问性 | 覆盖 360/390px 手机、768px 平板及 1280/1440px 桌面，浅深色、125% 缩放、系统大字体、软键盘、键盘导航及减少动态效果模式均实测。 |
| 数据恢复 | 建议最大可接受数据回退 1 小时、恢复服务 2 小时。用隔离环境从实际备份恢复并验证登录、近期消息、附件和权限，记录真实耗时。 |

### 千人规模怎么验证

首轮按 1,000 个账号、200 人同时在线、约 300 条 WebSocket 连接建模。持续场景用 300 条连接运行 8 小时，峰值用 500 条连接，另测服务重启后 300 条连接在 60 秒内重连。以每天 10,000 条消息估算，约 300 个活跃日可累积 300 万条。用这个量级的历史测试中文搜索、同时上传图片和 100 人群的消息广播。上述数字是容量假设，用实测活跃率和设备数校准。

优先复用现有 ASP.NET Core、Vue、WebSocket、SQLite 和消息窗口。先量出搜索耗时、写锁等待、广播积压、解码和重绘开销，再决定是否引入全文索引、缩略图服务或更复杂的存储架构。SQLite WAL 可并行读写，同一数据库仍只有一个写入者，迁移由实际写锁和故障恢复指标触发。评估 SQLite FTS5 trigram 时专门测中文两字词，保留适合短词的查询路径。 [SQLite WAL](https://www.sqlite.org/wal.html) · [SQLite FTS5 trigram](https://sqlite.org/fts5.html#the_trigram_tokenizer)

## 7. 迭代与上线顺序

1. **第一批先修基础。** 解决刷新白屏、明文记密、备份和探活。用固定测试对话跑一次浏览器、Windows 和 Android 的收发、重连与通知直达。记录现有切换、滚动和搜索基线。
2. **第二批做出一套可试用的聊天体验。** 先把消息首页、聊天详情和输入区做成亮暗两套可操作原型，再落地移动端更多菜单、未读锚点和状态反馈。用受控注册邀请 30–50 名已知用户试用，观察发信、发图、翻历史、回未读四条路径。
3. **第三批补齐消费场景。** 先完成 P0 的好友及群邀请、拉黑举报和权限测试，再交付多图、语音试听、表情回应和共享媒体。邀请 150–300 名来自不同亲友圈与兴趣群的用户连续使用两周。观察首条双向会话完成率、搜索打开目标的比例、漏提醒和发信失败。埋点只采操作结果、平台和耗时。
4. **达标后逐步扩到 1,000 人。** 按邀请批次扩大。每批复核消息错误率、通知到达、搜索性能和用户反馈。发现已确认消息丢失、越权读取或数据无法恢复时暂停扩大。

第一轮设计评审用两组相同内容的对话对比当前版与新方案。样例应包含未读、连续群消息、图片加载、语音、发送失败、引用跳转和键盘弹出。按原评审的六个维度复评，并以实际体验与验收数据为评分依据。
